# Grow the cause taxonomy before trusting memory

No existing public benchmark answers ELH's question as posed. None pairs labelled, recurring performance-regression causes with hidden graded oracles at a difficulty a 30B-A3B model can reach. The primary dataset should therefore be ELH's own generator, scaled from 5 causes to roughly 20 by adding SWE-smith-style performance-mutation operators to real repos. The memory-minus-static gap should then be measured as a function of cause count. Two external benchmarks serve as replication targets. AppWorld is the only place where an evolving context has already beaten an optimised static prompt (GEPA) with an open-weight model. LifelongAgentBench DB/OS offers 22 and 29 labelled skills and has already been run with open models up to 32B. The prior literature gives a clear warning. Papers that ran fair static controls show that a hand-written or all-in-context prompt often matches learned memory when lessons are few and tasks homogeneous, and several 2026 benchmarks report that memory systems fail to beat memory-off or naive in-context learning. With only 5 causes, the current harness sits in the regime where "all distilled rules in the system prompt" should recover most of the memory gain. A positive result there would not separate memory from a better prompt. The decisive experiments are a cause-count sweep, held-out-cause splits, and a frozen-final-memory-as-prompt control. No published paper runs that last control, so it would also be ELH's clearest contribution.

## Repo-level performance benchmarks sit at the floor for a 30B model

The obvious off-the-shelf candidates, GSO, SWE-Perf and SWE-fficiency, are real agentic repo-editing benchmarks with hidden correctness tests. They fail ELH's needs on three counts: difficulty, measurement noise and labels. GSO's **102 tasks** reach **under 5 percent Opt@1 for every model tested**, though Python-only tasks reach 21.4 percent ([GSO](https://arxiv.org/html/2505.23671v3)). SWE-Perf's 140 instances give open models such as Qwen3-235B and DeepSeek-R1 **0.5–0.9 percent performance** in the easier oracle setting ([SWE-Perf](https://arxiv.org/html/2507.12415v1)). On SWE-fficiency's 498 tasks, Qwen3 Coder Plus achieves **0.068x the expert speedup** ([SWE-fficiency](https://arxiv.org/html/2511.06090)). A July 2026 reliability audit then replayed 740 reference patches across four machine types. Only **39/102 GSO, 11/140 SWE-Perf and 411/498 SWE-fficiency** tasks kept their validity signal on every machine, and SWE-Perf's noise-to-signal ratio was **43x** ([audit](https://arxiv.org/html/2607.01211)). At those success rates, any memory-vs-prompt difference for Qwen3-Coder-30B-A3B would be lost in noise.

Labels are the deeper problem. Only SWE-fficiency ships a category, and it is an LM-assigned 9-way optimisation type (Algorithmic/Data-Structure, Memory, Caching & reuse, I/O, and so on) ([SWE-fficiency](https://arxiv.org/html/2511.06090)). Most of ELH's causes (quadratic membership, nested-scan join, `list.pop(0)` queues) would collapse into the single "Algorithmic" bucket, so one static hint would cover nearly all of them. The function-level efficiency sets have the opposite problem. PIE (77K C++ pairs), Mercury, EffiBench-X, EvalPerf and COFFE are large and cheap ([PIE](https://arxiv.org/pdf/2302.07867); [EffiBench-X](https://arxiv.org/pdf/2505.13004); [COFFE](https://arxiv.org/pdf/2502.02827)), but they are single-function rewrites drawn from heavily trained-on LeetCode/CodeNet sources, with no cause labels and trivial repository navigation. GSO's design is still worth borrowing: the performance test is given as the specification and correctness tests are hidden. Its documented "lazy", input-specific fast-path failure mode also matches the integrity dimension ELH already grades.

The verdict is to use SWE-fficiency only as a stretch realism split. Restrict it to replay-stable Python tasks in the Algorithmic and Caching categories and relabel them into ELH's fine-grained taxonomy by hand. Do not use GSO or SWE-Perf as primary evidence.

## A generated corpus is the only route to many labelled, uncontaminated causes

SWE-smith already provides most of the machinery ELH needs: per-repo Docker environments, a validation step that keeps only mutations with an observable effect, and generated issue text. It has produced **52K instances across 250+ images under an MIT licence** ([SWE-smith](https://github.com/SWE-bench/SWE-smith)). Every instance comes from a named strategy (LM-modify, LM-rewrite, AST procedural transforms, PR-mirror, combine). Per-strategy yield varies widely, from **1.93 percent for class-function shuffle to 47.04 percent for conditional inversion** ([SWE-smith paper](https://arxiv.org/pdf/2504.21798)), so operators will need tuning. SWE-smith generates only correctness bugs, and no public generator of *labelled performance regressions* turned up in the research. ELH would be filling an open niche, not duplicating one.

The extension adds performance-mutation operators, each tied to one cause label. Examples include set/dict lookup to list membership, hash join to nested scan, deque to `list.pop(0)`, a sort hoisted back into a loop, removed memoisation, quadratic string concatenation, an invariant recomputed in a loop, N+1 queries, catastrophic regex backtracking, pandas vectorisation replaced by `iterrows`, and repeated `re.compile` or `json` parsing. Each candidate is kept only if the existing tests still pass and a workload slows by more than *k*×. The un-mutated code is a known gold fix, and held-out causes give clean novel-cause transfer tests. SkillEvolBench offers the right family template: **6 tasks per family, sharing one underlying procedure but varying failure modes and surface forms** ([SkillEvolBench](https://arxiv.org/pdf/2605.24117)). In ELH terms, each cause recurs across different repos, identifiers, call depths and ways of exposing the slowdown, so retrieval has to match on the mechanism rather than the surface text.

Difficulty favours this design. Localisation is the hard part and the fix is a known idiom, so the 30–70 percent baseline band where both groups have room to move is reachable. For reference, 32B fine-tunes reach **40.2 percent** (SWE-agent-LM-32B) and **54.6 percent** (FrogBoss-32B) on SWE-bench Verified ([SWE-smith](https://github.com/SWE-bench/SWE-smith); [BugPilot](https://arxiv.org/abs/2510.19898)). Qwen3-Coder-30B-A3B's own Verified score could not be confirmed from a primary source, so it needs measuring. The strategy names in SWE-smith's correctness bugs also allow a cheap secondary repair experiment, with train/eval split by mutation type, without any new generation work.

## Continual-learning benchmarks supply external validity, but only two fit

Among the stream benchmarks, two clear ELH's bar of labelled families, local executability and an existing static or open-model baseline. **AppWorld** has 9 apps, 457 APIs and 750 tasks graded by state-based unit tests that also catch collateral damage ([AppWorld](https://arxiv.org/abs/2407.18901)). It holds the strongest prior evidence for the hypothesis. On it, with open-weight DeepSeek-V3.1, ACE's evolving playbook scored **59.5 average versus 46.4 for GEPA and 46.0 for ICL**, and **66.0 vs 46.0 TGC on test-challenge** ([ACE](https://arxiv.org/html/2510.04618v1)). The 457 API quirks are the kind of lesson diversity one static prompt struggles to hold. **LifelongAgentBench** has the richest explicit taxonomy: **DB 500 tasks/22 SQL skills, OS 500/29 Bash skills, KG 396/7 action types**. It was designed for inter-task relatedness and has already been run with Llama-3.1-8B/70B and Qwen2.5-7B/32B ([LifelongAgentBench](https://arxiv.org/html/2505.11942)). MemRL reports on its DB and OS splits ([MemRL](https://arxiv.org/html/2601.03192v2)), so ELH's MemRL reranking group would have a direct external comparison. Holding out whole skills gives a novel-category split that no coding benchmark ships ready-made.

The rest are cheaper or more realistic, but weaker fits. StreamBench offers single-turn streams (DS-1000 1,000, BIRD 1,534, Spider 2,147) graded by execution, with built-in zero-shot, few-shot and CoT static baselines. Its baseline rankings held across five random stream orders ([StreamBench](https://arxiv.org/html/2406.08747v1)), which makes it a cheap smoke test of the protocol but not an agentic one. SWE-Bench-CL orders 273 Verified tasks chronologically by repo, but the authors' own harness ran **below 8.5 percent, "making it impossible to draw reliable conclusions"** ([SWE-Bench-CL](https://arxiv.org/html/2507.00014v1)). VibeMemBench (111 targets, 3,634 history trajectories) is the most realistic coding memory test available and a valuable negative prior ([VibeMemBench](https://arxiv.org/abs/2609.23570)), but it is expensive and has no cause labels. Terminal-Bench 2.0 is too small for per-category streams at **89 tasks** ([evalscope](https://evalscope.readthedocs.io/en/v1.5.1/third_party/terminal_bench.html)). MemoryAgentBench measures conversational recall rather than procedural lessons ([MemoryAgentBench](https://arxiv.org/pdf/2507.05257)). Evo-Memory, ReasoningBank and MemRL all used API backbones only, so their absolute numbers will not carry over to a local 30B model ([Evo-Memory](https://arxiv.org/html/2511.20857v1); [ReasoningBank](https://arxiv.org/html/2509.25140v1)).

|---|---|---|---|---|---|
| ELH generator + SWE-smith perf operators | Yes, unlimited, ELH-defined | Yes | Yes (tunable) | ELH supplies | **Primary** |
| AppWorld | App/API, normal vs challenge | State unit tests | Likely; long context | ICL, GEPA, DC (ACE) | **Secondary replication** |
| LifelongAgentBench DB/OS | 22 + 29 skills | Auto-verified | Yes (Qwen2.5-32B run) | None; MemRL, replay | **Secondary replication** |
| StreamBench DS-1000/BIRD | Dataset-level only | Execution | Yes, cheap | Zero/few-shot, CoT | Protocol smoke test |
| SWE-fficiency (filtered) | 9 coarse LM labels | Yes | Near floor | None | Stretch realism split |
| SWE-Bench-CL / VibeMemBench | Repo, fix-time | Yes | Floor / costly | Memory-off | Optional, report as realism |
| GSO, SWE-Perf, Terminal-Bench | None or too few | Yes | Floor / too small | None | Avoid |

## Fair static controls usually narrow the memory advantage

The papers that ran a genuine static-prompt control give a consistent picture. Learned memory wins when lessons are many and heterogeneous. A well-built static prompt keeps pace when lessons are few. ExpeL's hand-written insights scored **32.0 on HotpotQA versus 39.0 for GPT-4-extracted insights** ([ExpeL](https://arxiv.org/html/2308.10144)). AWM's induced workflows reached **35.5 on WebArena against 33.0 for SteP's 14 expert-written workflows** ([AWM](https://arxiv.org/html/2409.07429)). In both cases the hand-written baseline was a real competitor, not a strawman. AutoGuide is the closest analogue to ELH's per-task WHEN-THEN retrieval. Retrieving conditional guidelines by context beat ExpeL's all-insights-in-prompt **79.1 vs 59.0 on ALFWorld and 46 vs 35 on WebShop**, with the widest gap on varied-domain WebArena (47.1 vs 21.8; the subset definition needs checking against the PDF). Accuracy also **peaked at k≈3 retrieved rules and fell from 47 to 43 at k=5** ([AutoGuide](https://arxiv.org/html/2403.08978)). Dynamic Cheatsheet shows the opposite regime. On homogeneous sequential AIME, a single cumulative cheatsheet (**50 percent**) beat retrieve-and-synthesise (**47 percent**), retrieval won only on the more diverse GPQA, and weak models (Haiku, GPT-4o-mini) gained little from either ([DC](https://arxiv.org/html/2504.07952v1)).

Task similarity drives the effect. Evo-Memory found ReMem's gain correlates with within-dataset similarity at **r=0.717 (Gemini 2.5 Flash) and r=0.563 (Claude 3.7)** ([Evo-Memory](https://arxiv.org/html/2511.20857v1)). MemRL found almost no gain (+0.4 percent) on low-similarity HLE ([MemRL](https://arxiv.org/html/2601.03192v2)). AgentCL found that only "dependent" streams discriminate memory designs, while independent streams show memory-induced degradation ([AgentCL](https://arxiv.org/abs/2606.02461)). The 2026 negative results set the null hypothesis firmly. Continual Learning Bench reports that **"naive ICL outperforms systems dedicated to memory management"** ([CL Bench](https://arxiv.org/abs/2606.05661)). VibeMemBench finds that **11 of 12 solver–memory pairings fail to beat memory-off** when the system must build its own experience; only pre-verified, directly injected experience helped, by 1.1–4.5 points ([VibeMemBench](https://arxiv.org/abs/2609.23570)). LifelongAgentBench's OS replay peaked at 4–16 trajectories and then declined ([LifelongAgentBench](https://arxiv.org/html/2505.11942)). MemRL's table may even show no-memory (0.860) beating every memory method on OS, though that row needs checking against the PDF ([MemRL](https://arxiv.org/html/2601.03192v2)).

Two cautions shape the static-prompt groups. First, ACE's win over GEPA is "rich, growing context beats short optimised prompt", not "retrieval beats prompt", because ACE keeps its whole playbook in context. ACE also documents "context collapse": a compressed rewrite from 18,282 to 122 tokens fell below baseline ([ACE](https://arxiv.org/html/2510.04618)). A GEPA arm that produces a terse prompt is therefore a weak control on its own, and an all-rules-static arm with no length cap is the stronger one. Second, the closest WHEN-THEN study, Learning on the Job, roughly tripled tau-bench banking success with corrections-driven rules, from **0.064 to 0.170**, against a static-RAG control. It still never tested "all learned rules in the system prompt" ([LotJ](https://arxiv.org/html/2607.22157)). No paper found compares a frozen final memory as a static prompt against per-task retrieval of the same rules. ELH can be first to run that control.

## Recommended plan: sweep cause count on generated tasks, replicate on AppWorld and LifelongAgentBench

**Primary dataset.** Extend the current generator to about 20 labelled causes by porting it onto SWE-smith's per-repo Docker pipeline and adding the perf-mutation operators above. Draw each cause from at least 6–8 repos with varied surface forms, following SkillEvolBench's family template. Keep the hidden oracle grading integrity, correctness and performance as today. Use CPU-pinned repeated timing with outlier removal, as SWE-Perf does, but with slowdowns of at least *k*× so noise cannot dominate. Calibrate the operators so the stateless baseline lands at 30–70 percent.

**Splits.** Each run has three evaluation slices: new instances of seen causes; seen causes in unseen repos; and wholly held-out causes. On held-out causes, expect memory and static prompts to converge. That convergence is itself a control, showing that gains on seen causes come from lessons rather than generic scaffolding. Report forward transfer, as in 2604.27003, and gains on baseline-never-solved tasks, following LotJ's 22/84 framing ([2604.27003](https://arxiv.org/html/2604.27003); [LotJ](https://arxiv.org/html/2607.22157)).

**Cause-count sweep.** Run K ∈ {2, 5, 10, 20} causes with total stream length and instances per cause held fixed, so per-cause exposure is matched. Repeat each K over at least 3 random cause subsets and 3 stream orderings. Plot memory minus all-rules-static against K, and separately against the token length of the frozen rule set. The hypothesis predicts a gap near zero at K=2–5 that widens as the rule set grows past what the model uses well. If the gap stays flat at K=20, the memory benefit is a better prompt rather than better retrieval. Add a within-K similarity manipulation: siblings within one Algorithmic family versus causes spread across Caching, I/O, pandas and regex families. This tests the Evo-Memory similarity effect directly. Run a top-k retrieval sweep (k = 0, 1, 3, 5, all) at K=20 to locate the AutoGuide knee for a 30B model.

**Control groups.** Every group shares the agent, tool budget and rollout budget. The table lists them in priority order.

| # | Control | What it isolates |
|---|---|---|
| 1 | Stateless baseline | Floor |
| 2 | Scaffold-only (memory instructions, empty store), per DC-empty | Prompt-structure effect |
| 3 | **All-rules-static**: final distilled WHEN-THEN rules from the memory run, frozen into the system prompt | Retrieval vs same content, the key control |
| 4 | Oracle-rule: only the rules for the task's true cause | Upper bound on retrieval |
| 5 | Wrong-cause rules, length-matched | Length and attention artefacts |
| 6 | Hand-written hints per cause (ExpeL hand-crafted / SteP analogue) | Human prior vs learned |
| 7 | Few-shot: fixed random exemplars vs task-similar retrieved exemplars | Exemplar retrieval vs rules |
| 8 | GEPA-optimised prompt and ACE offline playbook, trained on the same train split and rollout budget | Optimised static context |
| 9 | Memory groups: episodic + rules, + MemRL reranking, + AWM procedures | Treatments |

**Secondary replications.** On AppWorld, rerun the ACE comparison with Qwen3-Coder-30B-A3B. Add ELH's memory groups and controls 3–5 to the existing ICL/GEPA/ACE baselines, and hold out whole apps as the novel-category split. On LifelongAgentBench DB and OS, hold out skills, compare against MemRL's published protocol, and cap replay near the 4–16 trajectory optimum the authors observed. Use StreamBench DS-1000 first, as a one-day protocol smoke test. Put SWE-fficiency's filtered, replay-stable Python Algorithmic/Caching subset last, as a realism check reported separately, since floor effects are likely.

## Conclusion

The current 5-cause harness is a good start but cannot settle the question. At that size, the literature predicts a well-written static prompt will match memory, so a memory win at K=5 is ambiguous and a tie is the expected outcome. The question becomes answerable only when the number of distinct lessons is a controlled variable. That makes the generator the scientific instrument, not just a source of test tasks. It should support labelled causes in the tens, real-repo variety within each cause, and held-out causes.

The most useful single number ELH can publish is the slope of the memory-minus-all-rules-static gap against cause count, measured on the same distilled content. Prior work implies a slope but has never measured it. A flat slope would be the more surprising result, showing that for a frozen 30B coder, "memory" is mostly a way of writing a better system prompt. That result would matter for the project given the 2026 run of negative memory results. Two caveats apply. No 30B-class numbers exist on AppWorld, LifelongAgentBench or the perf benchmarks, and the small-model results from Dynamic Cheatsheet warn that a 30B-A3B model may apply retrieved lessons poorly. A pilot measuring baseline solve rates on each dataset should come before any of the sweeps.
