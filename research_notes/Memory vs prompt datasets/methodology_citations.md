## Recent benchmarks with unseen or obfuscated APIs and conventions for memory or continual learning (2024–2026)

I found no verified benchmark that uses a fully **fictional library** to evaluate **agent memory**. These are the closest:

1. **Continual Learning Bench (CL-Bench).** Asawa, Glaze, Orlanski, Ramakrishnan, Xu, Biswal, Chen, Sala, Zaharia, Gonzalez. arXiv:2606.05661 (June 2026; preprint, no venue found). Agents work through a sequence of instances in shared environments that have hidden structure. The Database Exploration task uses an *intentionally obfuscated schema* (for example, table `g2_reviews` and column `vrf` for verified status) whose conventions must be learned from experience. A Codebase Adaptation task covers repo-specific conventions. It compares memory systems with naive ICL and finds that naive ICL beats the dedicated memory systems. Project site per the paper: continual-learning-bench.com (not visited). **Closest match to the brief.**
2. **NovelAPIBench.** Liu, Peng, Niu, Wen, "NovelAPIBench: Diagnosing How A Code LLM Learns to Use Novel APIs," arXiv:2606.03657 (June 2026; preprint). Builds tasks around APIs a target model does not know: 1,670 tasks, 856 APIs, 21 libraries. Compares ways of delivering the knowledge (examples, signatures, retrieval). The APIs are real ones the model has not learned, not fictional ones, and memory or continual learning is **not** evaluated.
3. **SWE-Bench-CL.** Joshi, Chowdhury, Uysal, "SWE-Bench-CL: Continual Learning for Coding Agents," arXiv:2507.00014 (June 2025; preprint). Puts SWE-bench Verified issues in chronological order within each repo to measure accumulation, transfer and forgetting in a memory-enabled agent. Uses **real** repositories; nothing is fictional or hidden.

Also seen but not checked in depth: "To See is Not to Master: Teaching LLMs to Use Private Libraries for Code Generation" (PriCoder), arXiv:2603.15159 (2026, submitted to TOSEM). It uses recently released real libraries and compares fine-tuning on synthesized data with doc retrieval; it does not evaluate memory.

## Per-item notes and links

1. **Zan et al. 2022.** https://arxiv.org/abs/2210.17236 · https://aclanthology.org/2022.findings-emnlp.21/ · https://github.com/microsoft/PyCodeGPT. The paper says "we manually modified all library-related keywords in PandasEval and NumpyEval" and "manually paraphrased the descriptions of all the new APIs." The problems are 101 each. Your claim is right in substance. If the setup depends on the library *code* being renamed, check the repo: I did not confirm whether runnable `monkey`/`beatnum` packages are shipped.
2. **CodeUpdateArena.** https://arxiv.org/abs/2407.06249 · https://github.com/leo-liuzy/CodeUpdateArena. The updates are synthetic changes to real functions (54 functions, 7 packages). If you use it as a "prompt vs memory" reference, its headline result helps you: prepending the update docs did not fix the open models it tested.
3. **GitChameleon.** https://arxiv.org/abs/2411.05830 · https://arxiv.org/abs/2507.12367 · https://aclanthology.org/people/nizar-islah/ (2026.acl-long.2170). Real version differences, execution-based. Enterprise models score about 48–51% on 2.0.
