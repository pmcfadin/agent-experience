Study write-up · Experiential Learning Harness

Can AI agents become more experienced?

A frozen coding agent fixes generated performance bugs. Four agents differ only in what they keep between tasks. This write-up covers the hypothesis, the six papers each part of the design comes from, how we built them, what the evidence says so far, and what runs next.

Bottom line
  • Three independent learning histories confirm memory's gain on hard tickets, and show it depends on what the first episodes happen to teach. In experiment 13 (36 test tickets per arm), A fixed 6, B 26 and C 23. B won 21 paired tickets and lost 1; C won 18 and lost 1 (McNemar p < 0.001 for both; B used 0.21× A's GPU time per success, 95% interval 0.07–0.35). Per history, B fixed 11, 12 and 3 of 12. In the third history, no stored rule mentioned the ticket's second slow lookup, and the agents fixed only the first one.
  • MemRL's ranking (C) does not beat plain memory (B). Over three histories, B beat C on 6 paired tickets and lost 3 (p = 0.51). Over experiments 10, 11 and 13 together, B fixed 46 of 60 test tickets and C 43.
  • Memory with verbatim rules beats no memory on hard tickets, and the result replicated on fresh tickets. Across experiments 10 and 11 (24 test tickets), arm B fixed 20 and the agent without memory 7. B won 14 paired tickets and lost 1. Experiment 11 alone: B 12/12 against A 3/12 (McNemar p = 0.004; gain +75%, 95% interval +50% to +100%; 0.26× the GPU time per success, interval 0.08–0.53).
  • On a bug type the agent already handles, memory gives no pass-rate gain, but C made fixes cheaper. On nested_scan_join (experiment 12), A fixed 9 of 12, B 9 and C 10. C used 0.67× A's GPU time per success (95% interval 0.44–0.93), and both memory arms took about 8 fewer turns.
  • Procedures (arm D) did not add to C. D fixed 10 of 12 (p = 0.070 against A), and plain memory with rules (B) fixed 8 of 12 (p = 0.22). D's promotion check kept one of three procedures it tried, and it rejected the first for making protected-file breaks more frequent.
  • Our first version of Learning on the Job was unfaithful, and fixing it is part of this result. Hindsight had been paraphrasing each rule into facts, so in experiment 8b no rule wording ever reached the agent. Rules are now stored verbatim, with no model rewrite, and two memory slots are reserved for them, as the paper intends. Experiment 10 is the first run with this storage.
  • On hard tickets, memory helped in both earlier runs too. On quadratic-membership tickets, which the agent without memory almost always fails, the Hindsight arm fixed 5 of 12 against 1 of 12 (experiment 8a), and 7 of 12 against 3 of 12 with rules added (8b). Pooled over both runs, memory won 11 paired tickets and lost 3 (McNemar p = 0.057). It also used less wall time per episode (89–111 s against 138–179 s).
  • On easy tickets, memory hurt. On queue_pop_front, which the agent without memory fixes about 85% of the time, memory arms did worse in experiment 6 (A 8/10, B 6/10, C 5/10). Memory has room to help only where the agent fails without it.
  • Learning on the Job's rules may speed up learning, but the evidence is weak. With rules, the agent fixed 10 of 15 practice tickets, against 4 of 15 without (Fisher p = 0.066). On test tickets, 7 of 12 against 5 of 12 cannot be told apart. The baseline itself moved from 1 to 3 of 12 between runs.
  • Memory doesn't fix overwriting a protected file. The memory arm overwrote the protected examples/sample_output.json in 4 of 24 test episodes, against 2 of 24 without memory. It did so even after a rule naming the file was stored. On ticket 2008, the agent without memory passed in both runs and the memory arm failed in both, each time by overwriting that file.
  • All four arms are built from the cited papers: Hindsight as its paper intends, MemRL's usefulness ranking, Learning on the Job's rules, Agent Workflow Memory's procedures, and GEPA's reflective optimisation, plus the evaluation metrics from Moves to Memory. Each deviation from a paper is stated below.
What we are testing

The hypotheses

Primary hypothesis · H1
After 200 training episodes, the continuous-learning agent (D) achieves at least 20% lower fully loaded cost per verified success on sealed, unseen tasks than the stateless agent (A), without losing more than a preregistered margin of success rate.
cost per success = (inference + tool compute + memory service + reflection + validation + amortised learning) ÷ verified successes

D is 20% cheaper per success than A on sealed tasks

Design

The four arms

Every arm runs the same frozen model, system prompt, tools, sandbox, budgets (40 turns, 600,000 tokens) and judge. They differ only in what is carried from one episode to the next. Memory is shown once, at the start of an episode, inside the first message.

Research basis

From papers to code

Five agents read the papers your proposal cites, and their code where released, in parallel. Each wrote down the exact method: formulas, prompts, default settings and evaluation protocol. Six more agents then built each method in its own module, and I wired them together. Where we depart from a paper, the reason is given.

Hindsight

Latimer et al., ACL 2026 demo · arXiv 2512.12818 · vectorize-io/hindsight
The method
Memory organised by fact type (world facts, the agent's own experiences, observations), with retain, recall and reflect. Recall combines semantic, keyword, graph and time-based search, then a cross-encoder reranks. Reported 91.4 on LongMemEval-S and 89.6 on LoCoMo. It has no component ablations and does not cover learning from task outcomes.
What we found
Hindsight reranks each memory as "context: text". We had put the full ticket in the context, so the ticket filled the reranker's 512-token window and cut off the lesson. One protected-files lesson scored +0.78 with the ticket context and −9.32 on its own text.
What we built
Record format lesson-v3: a one-sentence outcome context with no ticket text, plus tags for outcome and failed checks. Recall can be limited to experience facts, the type the paper defines for what the agent did. Other additions: the full ranked candidate list with per-stage scores, bank missions, and a fingerprint that also covers context, metadata and mental models. elh/memory/hindsight.py
Effect on recall
Read-only replay on experiment 1's memory: lessons reached the top 5 in 1/10 test tickets as run, 8/10 when recalling experience facts only, and 10/10 with a fixed second "past mistakes" query. That second query is our own idea, not the paper's, so the paper-faithful arm B uses only the experience filter.
Deviations
We don't call reflect during episodes: it took 43 s and about 44,000 tokens per call in a probe. It remains a possible ablation.

MemRL

Zhang et al., arXiv 2601.03192 · MemTensor/MemRL
The method
Each memory is an intent, an experience and a usefulness value Q. Recall happens in two phases: keep memories whose task similarity passes a threshold, take the top k1, then rank by 0.5·z(similarity) + 0.5·z(Q) and inject the top k2. After each episode, every injected memory is updated as Q ← Q + 0.3(r − Q).
How strong
One run per setting, with no intervals. Gains over the strongest baseline were +3.8 points (runtime) and +2.8 (transfer). The large gains come from re-solving the same tasks over 10 rounds; on fresh coding tasks the gain was about 1–2 points. Our sample sizes should not assume MemRL-sized effects.
What we built
A reranker over Hindsight's own candidate list, with Q kept per source episode, so C differs from B only in ranking. Q survives snapshot restores and is hashed into each snapshot; test episodes rank with a frozen copy. Every ranking decision is logged. elh/learner/utility.py
Deviations
Reward: a pass scores 1 − cost/budget, as the spec says, but a failure scores −1, as in MemRL. With the spec's reward, a failure scores 0 and Q can never fall, so memories linked to failures are never demoted. The spec's version stays available as a setting.
Similarity gate: calibrated on our data (207 episode similarities, mean 0.865, sd 0.017). MemRL keeps about the top 20% of its whole store. Our candidates are already Hindsight's top list, about 14 episodes per ticket, so we set the gate at the 20th percentile (0.853). Otherwise about 3 episodes would remain for 5 slots.
Injection size: one memory per selected episode, so C shows as many memories as B.
The code's undocumented extras (random exploration, a −0.8 exclusion floor) are off, as in the paper.

Learning on the Job

Tablan, Taylor & Bernhem, arXiv 2607.22157
The method
After each episode, the agent reflects and writes one rule: "VERIFIED RULE: WHEN … THEN …" after a pass, "AVOID: …" after a failure. Each rule has a separate query field, phrased as the question a future agent would ask, which is what retrieval matches. A validator sends back rules that leave out key facts. The agent searches memory itself, once it has gathered information, and re-reads rules before acting. Reported 1.6× the no-memory baseline with verdict-only feedback, 2.6× with corrections.
Why it matters here
The authors' code notes that a single search on the opening message made a lesson unreachable, which is the failure we hit.
What we built
The rule writer, using the paper's reflection and rejection prompts adapted to tickets. The agent sees the judge's per-check verdict, the protected files it changed, and its time against the budget, but never the hidden tests or the reference fix. The validator requires the protected file names. There is also an optional search_memory tool; when it is off, every request is byte-identical to before (checked by a test). elh/learner/rules.py
Deviations
We have no gold solution, so the validator can only require the protected-file names. The merge of two conflicting rules is not implemented. In a sanity call, one rule gave a cause the prompt forbids it to guess, and no check caught it.

Agent Workflow Memory

Wang et al., ICML 2025 · arXiv 2409.07429
The method
A model turns successful runs into short reusable workflows: a description plus steps, with specifics replaced by placeholders. The whole library is regenerated after each success and shown in full, with no retrieval. On WebArena, success rose from 23.5% to 35.5% and steps per task fell from 7.9 to 5.9. Neither paper version reports seeds or variance.
What we built
Induction from passed training episodes only, one per ticket type, with steps taken from the agent's own commands and trimmed outputs. It uses AWM's induction prompt verbatim with three domain substitutions. Libraries are versioned in a skills table with their source episodes and hashes, and injected at the top of arm D's memory block. elh/learner/workflows.py
Added by the proposal
AWM promotes nothing; it just uses the new library. The proposal requires validation, so a candidate library runs against the current one on 6 held-aside development tasks, twice each. It is promoted only if mean reward improves, passes don't drop and protected-file breaks don't rise. It is rolled back automatically if a retention check drops.
Found in testing
On all 3 sanity calls the model copied the prompt's example workflows word for word, and a filter now drops those copies. Agents' real fixes often match the reference fix exactly, so those edits are shown as diffs and checked so that the reference text never leaks.

GEPA

Agrawal et al., ICLR 2026 · arXiv 2507.19457 · gepa 0.1.4
The method
Evolves a text prompt. A reflection model reads a few rollouts and their feedback, rewrites the text, and the rewrite is kept only if it scores better on those tasks. Candidates are chosen from a Pareto frontier across validation tasks. With Qwen3-8B it scored 54.85, against 48.91 for GRPO with 24,000 rollouts and 47.84 for MIPROv2. GEPA's coding-agent variant raised resolve rates from 55% to 82% and from 24% to 93%.
What we built
An adapter for the gepa package that optimises arm D's procedure text, scored with partial credit per check plus cost. A protected-file break scores 0. Feedback uses the judge's wording without reference timings, hidden inputs or the reference fix, and it runs on development tasks only. elh/learner/gepa_opt.py
Deviations
GEPA's default reflection prompt asks the model to keep "niche domain facts", which would copy ticket specifics into the procedure. We replaced it with one that tells the model to generalise. Merge is off, since it hurt Qwen3-8B in the paper. A pilot costs about 150 rollouts plus a 40-rollout check, roughly 3 hours on our single GPU.

When Continual Learning Moves to Memory

Hu, Long & Wang, arXiv 2604.27003
The method
Measures what memory does to an agent over time. Test tasks are split into those the baseline solves and those it fails. ΔRR measures whether memory breaks solved tasks; ΔNL whether it solves new ones. Forward and backward transfer are measured against a memory-enabled run that starts from scratch.
Its warnings
Raw trajectories cause negative transfer, worst on hard tasks (ΔNL −26). Fine-grained entries can collapse onto one item: 88.5% of searches returned the same top memory. The setting with the best forward transfer also forgot the most (−10).
What we built
ΔRR and ΔNL (hidden below 10 baseline failures, as in the paper), forward and backward transfer, hold rate (from Learning on the Job), a paired cluster bootstrap by task, and recall diagnostics: coverage, top-1 concentration, lesson reach and lesson rank. elh/analysis.py

Terminal-Bench was read for task design only. Our task format (hidden tests, reference solution, protected files) matches it. Two ideas are worth adopting: take the fastest of several timing runs to cut noise on a shared machine, and put canary strings in generated tasks.

Evidence so far

What the experiments show

Experiments 1 and 6 used one bug type, a job that pops items from the front of a Python list (queue_pop_front). Experiments 8a and 8b used a harder one, membership tests against a list (quadratic_membership). In each, memory arms trained on 15 tickets across five themes. All arms were then tested on 10 or 12 new tickets in a sixth theme, against a frozen snapshot of the memory.

Experiment 1 · void

The first memory format stated failures as their opposite

A failed protected-files check was written in the wording for the passing check: "FAILED: left the tests and harness untouched". Hindsight duly stored that the attempt "failed because it left the tests and harness untouched". Arm B then broke the protected-files rule in 3 of 10 test episodes, against 1 of 10 for arm A (A 9/10, B 7/10). We voided the result, fixed the wording (lesson-v2), and re-ran.

Every protected-file break in this experiment, in training and testing, was the same file, examples/sample_output.json. Every one came from the agent writing its verification output over the protected expected output. The recall fix worked: a protected-files lesson reached B in 9 of 10 test episodes, up from 1 of 10. It did not help. B passed 5 of the 9 episodes that saw the lesson, and in C's ticket 2003 the agent overwrote the file right after reading "failed because it modified protected files, specifically examples/sample_output.json".

Three readings fit this, and the next experiments are designed to separate them. First, the memories prime the behaviour: the most frequent memories all stress "byte-for-byte output equivalence", which invites checking against the sample file. Second, a lesson that names what not to do, without saying what to do instead, does not change behaviour; Learning on the Job's WHEN–THEN rules exist for this reason. Third, it is noise: with 10 tickets, 3 of 10 against 0 of 10 is suggestive, not conclusive. C's recall also concentrated onto one memory in 80% of test episodes, the collapse Moves to Memory warns about.

Neither run alone is significant, but both point the same way, and each run's interval for pass rate sits at or just below zero. Pooling the 24 paired test episodes gives p = 0.057. That pooling mixes B with and without rules, so it tests "any memory against none" rather than either arm. The baseline moved from 1 to 3 of 12 between runs (Fisher p = 0.59), which is ordinary noise at this sample size.

The rules were well formed. All 15 training episodes produced a rule. Successes wrote rules such as "WHEN a Python list membership check causes O(n²) time, THEN convert the list to a set for lookups and keep a separate list to preserve order." The first failed episode had already written a correct AVOID rule. In one case the format check rejected an AVOID rule because it left out the protected file's name. The agent rewrote it, and later still overwrote that file on a training ticket.

The agent used search. It called search_memory in 11 of 15 training episodes and 7 of 12 test episodes. Test episodes that searched passed 6 of 7, against 1 of 5 that didn't. The agent chose when to search, so this may reflect which tickets it found easy rather than what search contributed.

What rules may have changed. With rules, the agent fixed 10 of 15 training tickets, against 4 of 15 without them (Fisher p = 0.066), and wrong-output failures on test tickets fell from 3 to 0. Rules did not reduce protected-file breaks, which stayed at 2 of 12. All five remaining test failures were too slow, and two of them also broke the protected-files rule. Two tickets (2002, 2003) failed in all four arm-runs.

B against C. B beat C on 6 paired test tickets and lost 3 (McNemar p = 0.51). By history the split was 1–1, 2–0 and 3–2. MemRL's ranking adds nothing detectable to plain memory with rules.

Why the third history failed. These tickets have two slow list lookups: the obvious seen list and a second one, such as blocked. The test harness's speed check was not the cause: the reference program took a median 0.14 s in every history, and agent code either ran at about 1× the reference or timed out at about 20×. In histories 1 and 2, 31 of the 60 stored rules mentioned the second lookup. In history 3, none of the 30 did. Its first rules were AVOID rules about the seen list alone, and recall kept returning them. In 45 of history 3's 47 slow-code failures, the agent had added a set for seen and left the second list in place. Memory repeats what it has learned, and the order of the first few tickets decided whether that lesson was complete.

Cautions. The test tickets are the same in all three histories, so the pooled intervals treat the 12 tickets as clusters. Three histories are enough to show that histories differ, not to estimate how often a history learns an incomplete lesson.

Method notes

What went wrong, and what it taught us

Bugs that would have biased results

  • Failed checks described in their passing wording (experiment 1 voided).
  • Ticket text in the memory context made recall rank by ticket similarity.
  • A 500 KB scratch file in an episode diff caused about 40 memory-model calls; diffs now cover source files only.
  • Proposal formula for arm C's reward could never demote a memory linked to failures.
  • Learning on the Job's rules were paraphrased by Hindsight's fact extraction, so none reached the agent in their own words (experiment 8b, 0 of 587 candidates). Rules are now stored verbatim; experiment 9, which used the old storage, was stopped after 6 episodes.

Safeguards now in place

  • Model and memory LLM pinned by weights hash, build and context; checked before every episode.
  • Test episodes read a frozen snapshot of the memory, and must leave both its content hash and its learner hash unchanged.
  • Learners, rules and procedures never see hidden tests or the reference fix; tests check this.
  • Every earlier experiment setup keeps its exact hash, so old runs reproduce.
  • Each recall logs its full ranked candidate list, so "never retrieved" can be told from "retrieved but ignored".

Limits

What this evidence cannot show yet

  • Ten or twelve test tickets per arm. At a 90% pass rate, a 95% interval runs from about 60% to 98%. Only large effects are detectable, and the baseline moved by 2 of 12 between identical runs.
  • Few learning histories. Experiment 13 is the only run with several histories (three, on one bug type). Its histories ranged from 3 to 12 test tickets fixed for the same arm, so single-history results elsewhere in this report carry that much variation.
  • Placeholder prices. Cached input is priced at zero, although it is about 97% of input. Measured GPU time shows learning costs about 80–90% of inference; the placeholder ledger says 28%. Cost terms in rewards barely move.
  • Small comparisons have weak power. Moves to Memory withholds ΔNL below 10 baseline failures, and the published effects are a few points on fresh tasks (MemRL). The sample sizes for the confirmatory study need a power analysis on pilot variance.
Decisions

Open decisions

  1. Prices from GPU time. Replace the placeholder shadow prices with prices derived from measured GPU seconds. This changes the registration.
  2. Arm C reward. Adopt "pass: 1 − cost, fail: −1" and amend the spec, or keep the spec's formula as primary and report the other as a sensitivity run.
  3. GEPA promotion check. Use a larger development panel when GEPA is the procedure source, since with 6 tasks only 1 is unseen by its search.
  4. Reflect and mental models. Test Hindsight's reflect, or a standing "lessons from failures" mental model, as an ablation of arm B.
